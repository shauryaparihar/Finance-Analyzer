# Deployment

Frontend on Vercel, API on Render (Docker), PostgreSQL on a separate free provider (Neon suggested).

## Settings

| Variable | Where | Value |
|---|---|---|
| `ENVIRONMENT` | Render | `production` (turns on Secure cookies and strict startup checks) |
| `JWT_SECRET` | Render | generated by `render.yaml`; at least 32 characters, never the development default |
| `FRONTEND_URL` | Render | the exact production origin, `https://finance-analyzer-nu.vercel.app` (no trailing slash) |
| `EXTRA_FRONTEND_ORIGINS` | Render, optional | other exact https origins (custom domain), comma-separated, no wildcards |
| `DATABASE_URL` | Render, entered by hand | the PostgreSQL connection string; `postgres://` and `postgresql://` are accepted |
| other settings | optional | see `.env.example` |

Vercel needs no environment variables: the browser calls `/api/...` on the Vercel address and `vercel.json` rewrites it to the Render service. This keeps the login cookie on one origin.

## Order of steps

1. Create the database, copy its connection string.
2. On Render create the service from `render.yaml` (Blueprint), then paste `DATABASE_URL`.
3. The container applies migrations (`alembic upgrade head`) and starts. Check `/healthz` then `/readyz`.
4. Push the `vercel.json` rewrite; Vercel redeploys.
5. Run `python scripts/check_cookie_flow.py https://finance-analyzer-nu.vercel.app --check-replay`.
6. Do the browser checklist (register, upload, every screen, correction, review, delete, logout, cookie flags).

## Limits

Free hosting sleeps when idle (the first request can take about a minute). Migrations run at container start because the free plan has no pre-deploy command; with several instances use a pre-deploy command instead.
